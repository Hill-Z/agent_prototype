# Skill Studio 交互与渐进式配置设计

> 目标：把 Skill 从“复杂配置表单”设计成一个可渐进理解、可逐步生成、可沙箱验证、可安全发布的交付工作台。本文补充此前 Skill 设计中缺失的基础交互细节，尤其是渐进式加载、渐进式披露、按需展开、高级配置隔离、实时校验与调试闭环。

## 1. 核心判断

Skill Studio 不能把所有配置一次性摊开给前线工程师。复杂客服 Skill 可能包含触发、槽位、流程、工具、Prompt、Guardrail、Handoff、Memory、测试、发布等几十类配置，如果全部平铺，会导致：

- 新人不知道从哪里开始。
- 老手也很难定位问题。
- 高风险配置被误改。
- 配置项之间依赖关系不清楚。
- 每次修改都像在改一份巨型 JSON。

因此 Skill Studio 必须采用：

```text
渐进式加载 + 渐进式披露 + 向导式创建 + 专家模式 + 沙箱验证 + 发布门禁
```

一句话：

> 默认让用户只看到当前阶段必须做的事；只有当条件满足、风险升高、或用户主动展开时，才显示更复杂的配置。

## 2. Skill 配置的三层交互模型

### 2.1 新手向导层

面向第一次搭建或低复杂场景。

用户只需要回答：

```text
这个 Skill 解决什么问题？
什么用户话术会触发？
需要哪些信息？
需要查哪些系统？
成功时怎么回答？
失败时怎么办？
是否需要转人工？
```

平台自动生成：

```text
Skill 草稿
触发规则
槽位草稿
工具引用建议
基础回复策略
基础测试用例
```

### 2.2 标准配置层

面向大多数前线工程师。

展示 Skill 的主要模块：

```text
概览
触发
槽位
流程
工具
回复
风险
转人工
测试
发布
```

每个模块只展示常用项，高级项默认折叠。

### 2.3 专家模式层

面向资深交付、平台 PM、研发。

允许查看和编辑：

```text
完整 YAML/JSON
高级条件表达式
工具依赖 DAG
Prompt 拼装预览
Guardrail 策略细节
Trace 字段映射
版本 diff
回归测试结果
```

专家模式必须有权限控制和变更审计。

## 3. 渐进式加载设计

### 3.1 页面首屏只加载核心摘要

Skill 详情页首屏不应该加载全部配置。

首屏展示：

```text
Skill 名称
状态
版本
所属业务域
自动解决率
最近失败数
关联工具数量
发布状态
上次修改人
风险等级
```

不立即加载：

```text
完整 Prompt
完整测试用例
完整 Trace
历史版本 diff
大量 Mock 数据
复杂工具 schema
```

这些内容按 tab 或展开动作懒加载。

### 3.2 模块级懒加载

每个配置模块独立加载。

```text
打开“工具”tab -> 加载工具引用、schema 摘要、测试状态
展开某个工具 -> 加载完整 input/output schema、错误码映射、mock 数据
打开“测试”tab -> 加载测试集列表
点击某条测试 -> 加载执行详情和 trace
```

### 3.3 大对象按需加载

以下内容必须按需加载：

```text
Prompt 编译结果
Trace 明细
测试运行日志
工具原始返回
历史版本 diff
知识召回样本
多轮对话记录
```

避免 Skill 页面一打开就变慢。

## 4. 渐进式披露设计

### 4.1 默认只展示必要项

例如“工具引用”默认展示：

```text
工具名称
用途
调用时机
是否必需
最近测试状态
```

高级项折叠：

```text
超时
重试
幂等
脱敏
错误码映射
Trace 字段
并发策略
确认策略
```

### 4.2 按风险自动展开

如果 Skill 引用了高风险工具，系统自动展开相关配置，并强制检查：

```text
是否需要用户确认
是否需要审批
是否配置幂等键
是否配置回滚/补偿
是否配置敏感字段脱敏
是否有测试用例
```

例如：

```text
create_refund 被引用
-> 自动展开“确认策略”
-> 自动展开“权限与风险”
-> 自动展开“测试用例”
-> 发布前必须跑高风险用例
```

### 4.3 按错误自动展开

如果校验失败，直接定位并展开对应区域。

例如：

```text
发布检查失败：create_ticket 缺少失败兜底
-> 自动跳转到 工具 > create_ticket > 异常处理
```

### 4.4 按用户角色披露

不同角色看到的复杂度不同。

```text
客户运营：只看话术、知识、低风险转人工规则
前线工程师：看流程、槽位、工具引用、测试
平台研发：看 schema、Prompt 编译、Trace、Guardrail、版本兼容
```

## 5. Skill 创建向导

### 5.1 推荐步骤

```text
Step 1：选择业务场景
Step 2：描述用户问题
Step 3：选择/生成触发规则
Step 4：识别所需槽位
Step 5：选择工具
Step 6：编排处理流程
Step 7：配置回复策略
Step 8：配置风险与转人工
Step 9：生成测试用例
Step 10：进入沙箱试跑
```

### 5.2 每一步只问当前必要信息

不要一开始就要求用户填完所有字段。

例如创建“物流异常处理 Skill”时：

```text
先问：这个 Skill 处理什么用户问题？
再问：要不要查订单？
如果要查订单，再推荐 query_order 工具。
如果选择 query_order，再提示需要 order_id 槽位。
如果 order_id 缺失，再生成追问策略。
```

这就是配置里的条件式渐进。

## 6. 配置依赖联动

Skill 配置项之间必须联动，不能只是静态表单。

### 6.1 工具选择影响槽位

选择 `query_order` 后自动推荐：

```text
order_id
user_id
phone_last4
```

### 6.2 工具风险影响确认策略

选择写操作工具后自动要求：

```text
确认卡片
幂等键
权限规则
失败兜底
测试用例
```

### 6.3 渠道影响输出格式

选择微信/网页/APP 后自动限制：

```text
卡片能力
按钮能力
富文本能力
消息长度
是否支持附件
```

### 6.4 触发规则影响冲突检查

新增触发词后自动检测：

```text
是否与其他 Skill 冲突
是否覆盖过宽
是否容易误触发
```

## 7. 实时校验与发布检查

### 7.1 编辑时轻校验

边写边提示：

```text
槽位缺少来源
工具未配置异常兜底
高风险动作缺少确认
回复策略缺少工具证据约束
触发规则和已有 Skill 冲突
```

### 7.2 保存时结构校验

保存时检查：

```text
schema 合法
引用工具存在
变量引用存在
流程无断点
必填配置完整
```

### 7.3 发布前强校验

发布前必须检查：

```text
沙箱测试通过
高风险测试通过
Guardrail 通过
工具测试通过
回归测试通过
权限检查通过
版本 diff 已确认
```

## 8. 沙箱试跑交互

Skill 配置页必须内置沙箱，而不是另开一套割裂系统。

### 8.1 右侧实时试跑

左侧编辑，右侧试跑。

```text
输入模拟用户消息
查看命中的 Skill
查看槽位提取
查看工具调用
查看中间状态
查看最终回复
查看 Guardrail 命中
```

### 8.2 工具结果可切换

沙箱里可以切换：

```text
正常返回
空结果
超时
权限失败
schema 错误
业务错误码
```

### 8.3 Trace 可展开

默认只显示摘要：

```text
命中 Skill -> 收集槽位 -> 调用工具 -> 生成回复
```

点击后展开完整 trace。

## 9. Prompt 拼装预览

Prompt 不应该直接让前线工程师手写完整大 prompt，但必须让他们看到“最终拼出来的是什么”。

### 9.1 默认摘要

展示：

```text
系统角色
当前 Skill 规则
用户上下文
工具结果
输出要求
禁止事项
```

### 9.2 专家展开

专家模式可看：

```text
完整编译后 Prompt
Token 占用
各模块来源
冲突规则
被裁剪内容
```

### 9.3 变更 diff

修改 Skill 后展示 Prompt diff：

```text
本次修改影响了哪些 Prompt 片段
是否增加 token
是否改变工具使用规则
是否改变风险约束
```

---

## 10. 版本 diff 与影响分析

Skill 发布前必须让用户看到：

```text
改了什么
影响哪些触发规则
影响哪些工具调用
影响哪些测试用例
影响哪些渠道
影响哪些客户/租户
线上有多少会话可能受影响
```

默认展示业务 diff，不只展示 JSON diff。

例如：

```text
本次变更：
- 新增“物流 72 小时未更新”分支
- create_ticket 调用条件从“48 小时”改为“72 小时”
- 新增高风险失败兜底
- 影响 3 个测试用例，其中 1 个需要重跑
```

## 11. 空状态、加载态、错误态

### 11.1 空状态

不要只是空白。

```text
暂无工具引用 -> 推荐从 query_order / query_ticket 开始
暂无测试用例 -> 一键根据流程生成测试用例
暂无触发规则 -> 从历史会话中推荐触发表达
```

### 11.2 加载态

长加载必须显示具体内容。

```text
正在加载工具 schema
正在生成测试用例
正在编译 Prompt
正在运行沙箱测试
```

### 11.3 错误态

错误必须可行动。

```text
工具 query_order schema 加载失败
原因：工具版本 2.1 已废弃
操作：切换到 2.2 / 查看影响 / 联系负责人
```

## 12. 权限与协作体验

### 12.1 编辑锁

多人协作时需要：

```text
谁正在编辑
哪些模块被锁定
是否允许分模块并行编辑
如何合并冲突
```

### 12.2 评论与审核

支持对模块评论：

```text
对某个工具调用规则评论
对某条话术评论
对某个测试失败评论
```

### 12.3 审核流

高风险 Skill 发布需要：

```text
交付提交
平台审核
客户确认
灰度发布
```

## 14. MVP 必须做的交互能力

第一版至少要做：

```text
1. Skill 创建向导
2. 模块级折叠/展开
3. 高级配置默认隐藏
4. 工具选择后自动推荐槽位
5. 高风险工具自动展开确认配置
6. 右侧沙箱试跑
7. 实时校验
8. 发布前检查
9. Prompt 拼装预览
10. 版本 diff
```

## 15. 结论

Skill Studio 的关键不是“配置项多”，而是“复杂度如何被逐步暴露”。

好的 Skill Studio 应该做到：

```text
新手可以按向导完成 60 分配置
前线工程师可以在标准模式完成 80 分交付
专家可以在高级模式处理 95 分复杂场景
平台可以用发布门禁守住 100 分安全底线
```

所以文档必须补上：

```text
渐进式加载
渐进式披露
模块懒加载
按风险展开
按错误定位
按角色展示
配置依赖联动
沙箱内嵌
实时校验
发布门禁
```

否则 Skill 文档只是在讲“有哪些配置”，没有讲“复杂配置怎么被人正确使用”。

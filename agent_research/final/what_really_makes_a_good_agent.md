# 超越功能机制：什么才真正决定一个 Agent 做得好

> 文件：`C:\Users\13609\.codex\workbase\chat_agent\agent_research\final\what_really_makes_a_good_agent.md`  
> 目的：回答“即使做了 Skill、Tool、Hooks、Trace、Eval，为什么仍然不一定能做好 Agent？”  
> 结论：功能机制只是底盘，真正的 Agent 能力来自业务语义、任务设计、组织运营、数据飞轮、信任体验和持续优化系统。

---

## 0. 核心判断

做 Agent 最容易陷入一个误区：

> 以为把 Prompt、Tools、RAG、Memory、Workflow、Eval、Hooks 都做了，就能得到一个好 Agent。

这不对。

这些只是“Agent 平台能力”。真正决定 Agent 好不好的是：

```text
是否选对问题
是否理解业务
是否定义清楚边界
是否有可靠数据和系统动作
是否知道什么时候不自动化
是否能让用户信任
是否能被持续运营
是否能产生经济结果
```

一个差的 Agent，通常不是因为少一个 Hook，而是因为：

- 场景选错了。
- SOP 本身混乱。
- 客户数据不可用。
- API 不稳定。
- 转人工策略不合理。
- 业务指标没定义。
- 没有人负责持续运营。
- 评测集和真实用户脱节。
- Agent 被要求处理不该自动化的问题。

# 1. 第一层：问题选择，比技术架构更重要

## 1.1 好 Agent 先从“适合自动化的问题”开始

不是所有客服问题都适合 Agent。

适合第一期做的：

| 类型 | 特征 | 示例 |
|---|---|---|
| 高频重复 | 问题多、答案稳定 | 物流在哪、退款进度、会员权益 |
| 规则清晰 | SOP 明确，有标准答案 | 退货规则、配送时效 |
| 只读查询 | 可通过 API 查状态 | 订单、优惠券、工单进度 |
| 低风险动作 | 失败影响小，可回滚 | 创建咨询工单、预约登记 |
| 信息收集 | Agent 比人工更有耐心 | 售后信息、故障排查信息 |

不适合第一期做的：

| 类型 | 风险 |
|---|---|
| 高金额赔偿 | 业务责任大 |
| 法律/投诉纠纷 | 需要人类判断 |
| 规则经常变 | Agent 会过期 |
| 数据不可查 | 容易编造 |
| API 不稳定 | 用户体验差 |
| 客户内部没人维护 | 上线后必烂 |

## 1.2 产品经理要先做“可自动化性评分”

每个场景进入 Agent 前，应评分：

| 维度 | 说明 | 分值 |
|---|---|---|
| 频次 | 用户是否经常问 | 1-5 |
| 规则稳定性 | 答案是否稳定 | 1-5 |
| 数据可得性 | 是否有知识/API 支撑 | 1-5 |
| 风险 | 答错后果多大，反向计分 | 1-5 |
| 自动化收益 | 能节省多少人工 | 1-5 |
| 可评测性 | 是否能判断答对 | 1-5 |

优先级公式：

```text
优先级 = 频次 × 自动化收益 × 可评测性 × 数据可得性 / 风险
```

## 1.3 UAgent 应该产品化这个能力

新增功能：**场景可自动化评分器**

客户提出需求后，平台让 PM 填：

- 问题频次。
- 是否有 SOP。
- 是否有 API。
- 是否涉及资金/权益。
- 是否需要人类裁量。
- 答错后果。
- 是否能自动评测。

输出：

- 建议一期做。
- 建议二期做。
- 建议只做辅助人工。
- 建议不要自动化。

# 2. 第二层：业务语义建模，比 Prompt 更重要

## 2.1 好 Agent 需要业务本体，不只是自然语言

客服 Agent 必须理解业务对象：

```text
用户 User
会员 Member
订单 Order
包裹 Shipment
售后单 AfterSale
退款 Refund
优惠券 Coupon
商品 Product
门店 Store
工单 Ticket
人工客服 HumanAgent
```

如果平台只有 Prompt 和 Skill，没有业务对象模型，Agent 就会长期混乱。

## 2.2 业务对象应该有状态机

例如订单：

```text
created -> paid -> packed -> shipped -> delivered -> completed
                       -> cancelled
                       -> refunding -> refunded
```

退款：

```text
requested -> reviewing -> approved -> processing -> refunded -> rejected
```

投诉：

```text
created -> assigned -> negotiating -> escalated -> resolved -> closed
```

Agent 不应该只靠文本判断状态，而应该基于业务状态机生成回答和下一步动作。

## 2.3 UAgent 应该有“业务对象中心”

新增模块：**Business Object Center**

功能：

- 定义业务对象：Order、Refund、Coupon、Ticket。
- 定义字段：order_id、status、amount、delivery_time。
- 定义状态机。
- 定义状态可见性。
- 定义每个状态下 Agent 可说什么、可做什么。
- 映射 API 返回字段到业务对象。

示例：

```yaml
object: Refund
states:
  reviewing:
    user_message: 您的退款申请正在审核中
    allowed_actions:
      - query_refund_detail
    forbidden_claims:
      - 承诺具体到账时间
  refunded:
    user_message: 退款已完成，到账时间以支付渠道为准
    allowed_actions: []
```

## 2.4 为什么这比 Prompt 重要

Prompt 只能告诉模型“不要乱说”。

业务对象模型可以系统性保证：

- 只有状态支持时才说。
- 每种状态有固定话术边界。
- 工具结果可映射。
- 评测可自动判断。
- 前端卡片可稳定渲染。

# 3. 第三层：任务边界设计，比多 Agent 更重要

## 3.1 好 Agent 知道自己“不做什么”

很多 Agent 烂，不是因为不会回答，而是因为太爱回答。

客服 Agent 的成熟表现是：

- 该答时答。
- 该查时查。
- 该问时问。
- 该拒时拒。
- 该转人工时转人工。
- 不知道时不装懂。

## 3.2 要设计“自动化边界”

每个场景必须定义：

```yaml
can_answer:
  - 退货规则
  - 配送时效
can_query:
  - 订单状态
  - 退款进度
can_collect:
  - 售后原因
  - 联系方式
can_execute_with_confirmation:
  - 创建工单
must_handoff:
  - 赔偿
  - 法律威胁
  - 大额权益
must_refuse:
  - 查询他人隐私
  - 绕过规则
```

## 3.3 新增功能：Automation Boundary Designer

页面让 PM 配置：

- 自动回答范围。
- 自动查询范围。
- 自动执行范围。
- 需确认范围。
- 需人工范围。
- 禁止范围。

这比“安全提示词”更重要。

# 4. 第四层：对话产品体验，比模型聪明更重要

## 4.1 用户不关心 Agent 多智能，只关心过程是否可靠

用户体验好的 Agent 有这些特点：

1. 开场知道自己能做什么。
2. 不重复问已经知道的信息。
3. 问问题时一次只问关键问题。
4. 查系统时告诉用户正在查。
5. 查不到时解释原因和下一步。
6. 复杂问题能总结当前进展。
7. 转人工时不让用户从头说。
8. 不用“AI 味”话术敷衍。

## 4.2 UAgent 需要 Conversation UX Patterns

新增模块：**Conversation Pattern Library**

内置对话模式：

| 模式 | 场景 |
|---|---|
| 一问一答 | FAQ |
| 查状态 | 订单、物流、退款 |
| 信息收集 | 售后申请、预约 |
| 多选确认 | 多订单、多商品 |
| 失败降级 | 工具失败、查无结果 |
| 情绪安抚 | 投诉、焦虑、催促 |
| 人工交接 | 高风险、复杂问题 |
| 任务进度 | 多步流程 |

## 4.3 每种模式要有体验规范

例如“查状态”模式：

```text
1. 确认用户目标
2. 检查身份/变量
3. 告知正在查询
4. 展示核心状态
5. 解释状态含义
6. 给下一步建议
7. 提供人工入口
```

这类体验模式比单纯 Prompt 重要。

# 5. 第五层：数据和系统质量，决定 Agent 上限

## 5.1 Agent 不是魔法，客户后台烂，Agent 就会烂

如果客户有这些问题，Agent 很难做好：

- FAQ 过期。
- SOP 互相冲突。
- 订单 API 慢。
- 退款状态不准。
- 商品数据缺字段。
- 活动规则临时变。
- 客服团队自己都解释不一致。

## 5.2 UAgent 应该做“Agent Readiness Check”

客户上线前做 readiness 评估：

| 检查项 | 结果 |
|---|---|
| 是否有最新 SOP | 是/否 |
| 是否有历史会话 | 是/否 |
| API 是否有测试环境 | 是/否 |
| API P95 延迟 | 数值 |
| 是否有错误码文档 | 是/否 |
| 是否有人工兜底队列 | 是/否 |
| 是否有知识维护 Owner | 是/否 |
| 是否有业务验收人 | 是/否 |

输出：

- 可上线。
- 可试点但有风险。
- 不建议上线，先补资料/API/SOP。

## 5.3 这是商业上很重要的功能

它可以避免销售过度承诺，也能帮客户理解：

> Agent 做不好，不是模型不行，而是业务数据基础不够。

# 6. 第六层：运营机制，比上线更重要

## 6.1 Agent 是“数字员工”，不是“一次性交付软件”

一个客服 Agent 上线后会持续遇到：

- 新活动。
- 新商品。
- 新政策。
- 新异常。
- 用户新问法。
- API 改动。
- 渠道变化。

如果没有运营机制，Agent 会自然腐烂。

## 6.2 需要 AgentOps 角色体系

| 角色 | 职责 |
|---|---|
| Agent Owner | 对业务指标负责 |
| Knowledge Owner | 维护知识正确性 |
| Skill Owner | 维护能力包 |
| Action Owner | 维护工具/API |
| QA/Eval Owner | 维护评测集 |
| Handoff Owner | 维护人工接管规则 |
| Compliance Owner | 维护风险边界 |

## 6.3 UAgent 应该有 AgentOps 工作台

功能：

- 每周优化待办。
- 知识缺口。
- Skill 失败。
- 工具异常。
- 转人工原因。
- 评测退化。
- 成本异常。
- Owner 分派。
- SLA 追踪。

## 6.4 Agent 健康分

设计 Agent Health Score：

```text
Agent Health = 解决率 × 满意度 × 安全通过率 × 工具成功率 × 知识新鲜度 / 成本异常系数
```

比单看会话量有用得多。

# 7. 第七层：评测哲学，比评测工具更重要

## 7.1 Eval 不是为了证明 Agent 好，而是为了发现它在哪些地方会坏

很多团队做 Eval 只是跑好看的通过率，这没意义。

好的 Eval 应该包含：

- 真实高频问题。
- 近邻误触发问题。
- 工具失败问题。
- 用户口语、错别字、省略表达。
- 恶意/越权问题。
- 业务边界问题。
- 历史事故问题。
- 渠道格式问题。

## 7.2 UAgent 应该有 Eval Coverage Map

不是只显示通过率，而是显示覆盖度：

| 维度 | 覆盖情况 |
|---|---|
| Top 20 高频问题 | 覆盖 18/20 |
| 高风险场景 | 覆盖 12/12 |
| 工具错误码 | 覆盖 8/15 |
| 渠道格式 | 覆盖 3/5 |
| 用户情绪 | 覆盖 4/8 |
| 历史失败 | 覆盖 32/32 |

## 7.3 Eval 要绑定真实业务分布

用例不应平均分配，而应和真实流量有关：

- 物流 40%。
- 退款 20%。
- 会员 15%。
- 商品 15%。
- 投诉 10%。

评测报告要给加权得分。

# 8. 第八层：经济模型，决定客户是否长期付费

## 8.1 好 Agent 必须能证明 ROI

企业客户最终会问：

- 少了多少人工？
- 多解决了多少问题？
- 每解决成本是多少？
- 有没有降低投诉？
- 有没有提升转化？
- 有没有减少质检风险？

## 8.2 UAgent 应该有 ROI Simulator

上线前预测：

```text
月咨询量：100,000
可自动化比例：45%
预期自动解决率：60%
人工单次成本：3 元
模型/工具单次成本：0.15 元
预计节省：100000 × 45% × 60% × (3 - 0.15)
```

上线后对比真实结果。

## 8.3 商业化重点

不是卖“Agent 数量”，而是卖：

- 自动解决量。
- 节省人工。
- 安全合规。
- 行业方案。
- 运营闭环。

# 9. 第九层：信任设计，决定用户是否敢用

## 9.1 用户信任来自可解释、可控、可退出

Agent 应该让用户知道：

- 它能做什么。
- 它正在做什么。
- 它依据什么回答。
- 它什么时候会转人工。
- 用户怎么纠正它。
- 用户怎么退出自动流程。

## 9.2 信任体验功能

新增：**Trust UX Kit**

功能：

- 引用来源展示。
- “正在查询订单”的进度提示。
- 高风险动作确认卡。
- “为什么转人工”说明。
- “这个回答有帮助吗”。
- 用户纠错入口。
- 人工接管按钮常驻。
- 数据使用说明。

## 9.3 客服场景尤其重要

客服用户往往已经焦虑。Agent 如果装懂、绕圈、不给人工入口，会显著激怒用户。

# 10. 第十层：组织能力，决定平台能不能规模化

## 10.1 前线工程师写 Skill 不是终局

合理分工应该是：

| 阶段 | 主责 |
|---|---|
| 业务目标 | PM + 客户业务负责人 |
| 场景拆解 | PM + 解决方案 |
| API 工具 | 工程 |
| Skill 草稿 | Skill Copilot + 解决方案 |
| 业务审核 | 客户业务负责人 |
| Eval | QA + PM |
| 上线 | PM + 工程 + 客户 |
| 运营 | AgentOps |

## 10.2 UAgent 应该提供协作流

- 需求澄清表。
- 场景地图。
- Skill review。
- Eval review。
- 发布审批。
- 线上优化任务。
- Owner 和 SLA。

否则平台再强，也会变成“谁会写 Prompt 谁负责”。

---

# 11. 第十一层：客户成功方法论，比平台功能更早产生价值

## 11.1 客户第一次成功要小

不要一上来做“全能客服 Agent”。

建议首个试点满足：

- 2-3 个高频场景。
- 只读查询为主。
- 有明确 API。
- 有人工兜底。
- 有 2 周灰度。
- 有明确 ROI 指标。

## 11.2 UAgent 应该有 Onboarding Playbook

客户上线流程：

```text
Day 1: 需求澄清 + readiness check
Day 2: 场景拆解 + 数据/API 盘点
Day 3: 配知识 + 配 Action
Day 4: 生成 Skill + Eval
Day 5: 沙箱调试
Day 6-7: 客户验收
Week 2: 灰度上线
Week 3: 复盘优化
```

## 11.3 产品要支持“交付即沉淀”

每交付一个客户，都沉淀：

- 行业模板。
- Topic 样例。
- Skill。
- Action。
- Eval。
- Guardrail。
- ROI benchmark。

这样平台才会越做越强。

# 12. 第十二层：模型选择与策略，不只是接哪个大模型

## 12.1 好 Agent 通常不是一个模型跑到底

不同任务应使用不同策略：

| 任务 | 模型策略 |
|---|---|
| 意图识别 | 快模型 + 结构化输出 |
| FAQ 回答 | 中模型 + RAG |
| 高风险决策 | 强模型 + reflection |
| 格式化 | 小模型或代码 |
| 评测生成 | 强模型离线 |
| 安全检查 | 专门分类器/规则 + 模型 |

## 12.2 UAgent 需要 Model Policy

配置：

- 每个 Topic 使用什么模型。
- 高风险是否升级模型。
- 低价值场景是否降级模型。
- 成本超限如何降级。
- 不同模型输出差异如何评测。

## 12.3 模型不是核心壁垒

模型会越来越强，但企业 Agent 的壁垒在：

- 业务对象。
- 交付方法。
- 评测数据。
- 运营闭环。
- 行业模板。
- 客户系统连接。

# 13. 第十三层：从“Agent 搭建平台”升级为“Agent 经营系统”

### Level 2：能治理

- Eval。

UAgent 要做强，必须从 Level 2 走到 Level 3。

# 15. 最终判断

一个好 Agent 不是由“功能堆叠”产生的，而是由这几个系统共同产生的：

```text
选对业务问题
  + 建立业务语义模型
  + 设计清晰自动化边界
  + 接入可靠知识和系统
  + 提供可信对话体验
  + 建立评测和回归体系
  + 配套运营组织
  + 证明经济价值
  + 持续从失败中学习
```

所以 UAgent 的产品路线不能只是：

> Prompt -> Skill -> Tool -> Workflow

而应该升级为：

> 业务场景经营系统 -> Agent 工业化生产系统 -> AgentOps 运营系统 -> ROI 结果系统

这才是从“能搭 Agent”到“能做好 Agent”的差别。
